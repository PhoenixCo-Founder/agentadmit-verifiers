# AgentAdmit verifiers

Offline, dependency-free verifiers for the records the [AgentAdmit](https://agentadmit.com) hosted service exports: the tamper-evident consent trail, the tamper-evident per-call audit trail, and verifiable consent evidence (a user-verified passkey signature over a commitment to exactly what was approved).

They exist so that an auditor, a customer's security team, or anyone holding an export can check it **without trusting AgentAdmit**. Nothing here calls the network. Nothing here needs an AgentAdmit account. Every check is also written out in plain language in [FORMATS.md](FORMATS.md) so you can re-implement it in your own tooling; these scripts are the reference, not the only way.

| Verifier | Input | Proves |
| --- | --- | --- |
| `verify_consent_chain.py` | `GET /api/v1/consent/export` | Every decision event on the consent trail is intact, in order, and continuous from genesis. A deleted, altered, or reordered event breaks every later fingerprint. |
| `verify_audit_chain.py` | `GET /api/v1/audit/export` | Every verified call in the per-call audit trail is intact, ordered, and continuous; a first row that points into pruned history is reported as an anchor, not a failure. |
| `verify-consent-evidence.mjs` | `GET /api/v1/connections/{id}/evidence?include_raw=true`, a consent export, or a bare evidence object | A user-verified WebAuthn ceremony (Face ID, Touch ID, Windows Hello, a security key) signed a commitment to the exact recorded parameters: a grant, a confirm-each-time action, a consent-switch change, or a protective-boundary change. |

## Run

Python 3.8+ and Node.js 18+; standard library only.

```bash
# consent trail
curl -s 'https://agentadmit.com/api/v1/consent/export?environment=live&format=json&limit=10000' \
  -H "Authorization: Bearer $AGENTADMIT_API_KEY" -o consent-export.json
python3 verify_consent_chain.py consent-export.json

# per-call audit trail
curl -s 'https://agentadmit.com/api/v1/audit/export?environment=live&format=json&limit=10000' \
  -H "Authorization: Bearer $AGENTADMIT_API_KEY" -o audit-export.json
python3 verify_audit_chain.py audit-export.json

# passkey evidence for one connection, bound to values you already hold
curl -s 'https://agentadmit.com/api/v1/connections/conn_.../evidence?include_raw=true' \
  -H "Authorization: Bearer $AGENTADMIT_API_KEY" -o evidence.json
node verify-consent-evidence.mjs evidence.json --expect '{"scopes":["read:profile"],"duration":"30d"}'

# every ceremony recorded in a consent export
node verify-consent-evidence.mjs consent-export.json
```

Exports are paginated. Concatenate pages in export order before verifying. For continuity checks export the whole app/environment segment for your window; the `connection_id` and `app_user_id` filters intentionally skip interleaved rows and will look like gaps.

Exit codes: `0` valid, `1` a check failed, `2` the input was not a recognized export.

Relying party: the checks pin the WebAuthn origin and rpId to the hosted service (`https://agentadmit.com`). A bundle that declares its own `rp_id`/`origin` (a preview or private deployment) is checked against those, and `--rp-id` / `--origin` override both.

Legacy records: evidence written before authenticator assurance tiers shipped (`v: 1`, `ceremony: registration`) contains a commitment-bound enrollment but no assertion signature. The verifier checks its structure, says so plainly, and exits `0` with `EVIDENCE CHECKED` rather than `EVIDENCE VALID`.

## Self-test

```bash
./run-fixtures.sh
```

`fixtures/` holds synthetic exports and evidence generated by `fixtures/generate.mjs` with a throwaway P-256 key. The matrix includes deliberately broken fixtures (a deleted row, an altered row, a commitment edited after signing) that must fail. Regenerate with `node fixtures/generate.mjs`.

## What is independent here

The consent and audit chain verifiers recompute SHA-256 fingerprints from the exported chain inputs. They contain no knowledge of the AgentAdmit service or its database, and they work on any export copy held outside the service.

The consent evidence verifier (`verify-consent-evidence.mjs`) applies WebAuthn assertion verification: it checks that a user-verified passkey signed a commitment to the exact recorded parameters. By default it uses the authenticator public key carried in the export (`evidence.public_key`), which means verification trusts the export for that field.

**To remove that dependency**, supply your own copy of the authenticator public key with `--trust <file.json>`. A trust file is a JSON array (or object) you create from your own enrollment records, kept in your own secure store independently of the export under review. The auditor is responsible for authenticating that enrollment record. When `--trust` is provided, the verifier checks that `evidence.public_key` matches your trusted key and uses your key for the ECDSA P-256 signature check. Only auditor-supplied keys are used for the signature check. An explicit `credential_id` limits a key to that credential; unscoped keys are tried until one verifies. A missing file argument, an unmatched credential, or unsigned legacy registration evidence fails trusted verification. JWK keys must specify EC P-256 (and ES256 if `alg` is present).

The relying party (rpId and origin) can also be supplied independently via `--rp-id` / `--origin` or inside the trust file, removing any dependency on the defaults carried in the export.

## What a pass means, and what it does not

- **Tamper-evident, never tamper-proof.** A self-consistent export proves that nothing inside it was deleted, altered, or reordered. It cannot prove completeness, and an operator who rewrites and re-chains history is caught only by comparing exports taken at different times. Keep exports outside the operational database.
- **Evidence proves what was signed.** A valid evidence record proves that a user-verified authenticator signed a commitment to these recorded parameters, at the hosted origin, for the hosted relying party. No cryptography can prove what a screen rendered. Treat evidence as a review-time record, never an enforcement input.
- **Records are not authority.** An export or an evidence bundle never authorizes a new action. Every allow is a live check against the current grant.
- **Consumer tier is labeled.** Evidence carries an `assurance` record. `user_verified_unattested` means a phone or synced passkey; `trusted_attestation` means a hardware key whose attestation was validated against the FIDO Metadata Service. The verifier reports the tier; it does not upgrade it.

## Formats and versioning

Export bodies carry `format_version`. Additive fields never bump it; a renamed, removed, or re-defined field does. Each verifier prints the version it saw and warns when an export is newer than it understands. Field tables and the exact commitment layouts are in [FORMATS.md](FORMATS.md).

## Keeping these in sync with the service

These scripts are the published copy of the verifiers the AgentAdmit test suite runs against synthetic chains. Before publication they were also run against real hosted ceremonies from the AgentAdmit and TrainerTracer production records (a grant, a confirm-each-time action, and a legacy v1 record) and passed every check. A change to an export format lands here in the same release, with a `format_version` bump when the change is not additive.
